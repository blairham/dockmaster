# AGENTS.md — dockmaster

Guidance for AI coding agents (Claude Code, Cursor, Copilot, Codex, OpenCode, …) working in this repository. This is the **cross-tool single source of truth** — `CLAUDE.md` imports it.

## Project Overview

**dockmaster** is a k9s-style terminal UI for Docker: containers, images, volumes, networks, and Compose projects in one navigable frame, with live log tailing, inspect, and the full container lifecycle on the keyboard. On a Colima host it also manages the VMs (profiles) under the daemon.

- Module path: `github.com/blairham/dockmaster`
- Go 1.26 (pinned in `.tool-versions`, kept in sync with `go.mod` by a pre-commit hook)
- Built on [`github.com/blairham/tuikit`](https://github.com/blairham/tuikit) — the shared Bubble Tea chrome — plus the Docker Engine API client (`github.com/moby/moby/client` and `.../api`).

**Hosted at `github.com/blairham/dockmaster`**, Apache-2.0. CI (`.github/workflows/ci.yml`) runs pre-commit, `go test -race -short ./...` and a darwin/linux cross-compile; CodeQL and OpenSSF Scorecard run alongside. Every user-visible change adds a line under `[Unreleased]` in `CHANGELOG.md`; a release moves it to the version's section in a PR first, because the release notes *are* that section (`--release-notes`; the job fails when the tag has none). A signed `v*` tag releases through GoReleaser (`.github/workflows/release.yml`): darwin/linux archives, a cosign-signed `checksums.txt`, SLSA build provenance (`actions/attest-build-provenance`, attached as `dockmaster-<tag>.intoto.jsonl`), and the `dockmaster` formula (with the `dm` symlink) in `blairham/homebrew-tap`, which needs the `HOMEBREW_TAP_TOKEN` secret. Releases start at `v0.0.0`.

⚠️ **tuikit's module path is `github.com/blairham/tuikit`, and it is public** — it needs no `GOPRIVATE` entry.

## Quick Reference

```bash
make help                 # list targets
make build                # ./dist/dockmaster
make install              # build + copy to ~/.local/bin, plus a dm -> dockmaster symlink
make run ARGS='--readonly'
make screenshots          # re-render docs/images with VHS on a staged demo daemon (DEMO_HOST=...)

make check                # fmt + vet + test
make test                 # go test -race ./...
go test -short ./...      # skip the live-daemon tests (see below)

go run . --context colima # run against a specific docker context
```

**`go test -short` matters here.** `internal/docker/live_test.go` talks to a real daemon; it self-skips when none is reachable, but on a slow VM-backed daemon the image listing alone can take minutes. `-short` skips those and leaves the whole pure-logic suite, which needs no docker at all.

**Never run `golangci-lint` by hand.** There is no `make lint` target — it runs as a pre-commit hook and nowhere else, so a failing lint fails your commit and you fix it and commit again. That is the only lint output to read.

⚠️ **`fieldalignment -fix` reorders struct fields and does NOT rewrite positional composite literals to match.** It has already silently swapped two fields of a test table here, turning every case into a type error. `govet`'s `fieldalignment` is enabled in `.golangci.yml`, so `golangci-lint run --fix` applies it — one more reason not to run the linter by hand. Write struct literals with **named fields** — the test tables all do, and the comment in `internal/docker/docker_test.go` says why.

## Code Conventions

- **`main.go` is the only file in package `main`**, so `go run main.go` builds as well as `go run .`. Helpers go in an `internal/` package.
- **`internal/docker` and `internal/colima` must not import bubbletea.** They return plain values and errors; views wrap them in messages. That boundary is what lets each be tested against the real thing with no TUI in the loop.
- **Views never mutate.** `View.HandleKey` returns an `(action, param)` pair; `App.handleAction` carries it out. This is not ceremony — it is why `--readonly` is a single map lookup in one function rather than a flag threaded through nine views. Adding a mutation to a view directly defeats it.
- **Every destructive action goes through `chrome.Confirm`.** No exceptions, including ones that "obviously" cannot lose data.
- goimports local-prefix is `github.com/blairham/dockmaster`; internal imports get their own group.
- golines max-len 120. misspell locale US.
- **The lint config carries no adoption-relaxation block.** dockmaster started green at the canonical thresholds and should stay there — a genuinely flat dispatch function takes a targeted `//nolint` naming the reason, not a globally disabled linter.
- Apache-2.0, `LICENSE` and `NOTICE` in Blair Hamilton's name. Every `.go` file starts with the two-line SPDX header; contributions need the CLA (`CLA.md`).

## The docker context store — the thing that is easy to get wrong

The Go SDK's `client.FromEnv` reads **only the environment** — `DOCKER_HOST`, plus `DOCKER_API_VERSION`, `DOCKER_CERT_PATH` and `DOCKER_TLS_VERIFY` (#35). It does not read docker *contexts*. On any machine using Colima, Rancher Desktop, Podman, or a remote host — where the endpoint lives in the context store and nowhere else — an SDK program therefore dials `/var/run/docker.sock` and reports "is the docker daemon running?" while `docker ps` two lines earlier worked fine.

`internal/docker/context.go` closes that gap, following the CLI's own precedence:

1. `--host`
2. `$DOCKER_HOST`
3. `$DOCKER_CONTEXT`, looked up in the store
4. `currentContext` from `~/.docker/config.json`, looked up in the store
5. the platform default socket

The store lives at `~/.docker/contexts/meta/<hex sha256 of the context name>/meta.json`. `TestContextDigestMatchesDockerCLI` pins that digest scheme against a real value, because if it ever drifts the failure is silent: dockmaster falls back to the default socket and declares a live daemon dead.

A context's endpoint is more than its host (`internal/docker/endpoint.go`, #33, #34): its TLS files under `contexts/tls/<digest>/docker/` and `SkipTLSVerify` become the client's TLS config (`contextTLS`, the CLI's rules — a `ca.pem` replaces the system roots), and an `ssh://` host is dialed by running `ssh … docker system dial-stdio`, the CLI's connection helper, since the SDK has none. TLS is found by context *name*, so `--context` and `:ctx` dial with `NewForContext(name, host)`, and the docker CLI is pointed at the daemon with `Client.EndpointArgs` — `--context <name>` for a TLS context, else `--host`. The scanner, kind and plugins still get only the host. See `docs/design/docker-context-resolution.md`.

`ctrl-d` in the contexts view is `docker context rm <name>` (`docker.RemoveContext`, the CLI exec'd with the name as one argument, no shell) after a confirm naming it. `App.confirmRemoveContext` refuses `default`, the context dockmaster is connected through and the CLI's current one (`Context.Current`) first, with the reason; `confirm_remove_context` is in `mutating`, and the result refreshes the contexts view. Tests put a fake `docker` on PATH and never touch the user's store.

## Daemon calls are slow, and the design assumes it

This is not a theoretical concern. On a Colima host measured during development:

| Call | Time |
|---|---|
| `_ping` | instant |
| `docker ps` (7 containers) | ~6 s |
| `docker images` (651 images) | **did not complete — timed out at 300 s, twice** |

Both were as slow through the CLI as through the SDK, so it is the daemon, not the client. Three consequences are baked in and must not be undone:

- **Every list view single-flights its refresh** (`inFlight` guard). The 3-second poll skips entirely while a request is outstanding. Without it, a 6-second `ps` on a 3-second tick stacks requests until the socket refuses connections.
- **The poll is 3 s, not k9s's 2 s**, and `imageListTimeout` is 5 minutes while everything else is 20–60 s. On the host above even that is not enough, and the images view surfaces a timeout with a hint rather than spinning forever — a daemon that cannot list its own images in five minutes is a daemon problem, and dockmaster says so instead of hiding it.
- **Every daemon request takes its deadline from `Client.RequestContext(def)`**, never a bare `context.WithTimeout`: `--request-timeout` / `requestTimeout` overrides `def` everywhere, and a guard test counts the exceptions (CLI calls only).
- **The CPU/MEM sampler is one blocking request per running container** and is togglable with `<t>` for exactly that reason.

The stats sampler asks for the two-sample form — `ContainerStatsOptions{Stream: false, IncludePreviousSample: true}` — **not** one-shot, which is what the zero value sends. One-shot returns a zeroed `PreCPU` block, and the CPU formula against a zero baseline reports numbers in the thousands of percent. `TestLiveStats` asserts a plausible bound to catch a regression back to it.

## Keymap

Digits `0`–`6` switch resources, numbered from 0 as in k9s (`5` is Runtimes: Colima, Podman, Docker Desktop, Rancher Desktop, OrbStack; `6` is Events). Within a view:

| Key | Action | Key | Action |
|---|---|---|---|
| `enter` | drill in (logs / layers / inspect) | `o` | inspect |
| `u` | start ("up") | `x` | stop |
| `R` | restart | `K` | kill (SIGKILL, confirms) |
| `p` | pause / unpause (flips with state) | `s` | shell into the container |
| `a` | toggle stopped/all | `t` | toggle the CPU/MEM poll |
| `z` | volume sizes (slow, off by default) | `P` | prune |
| `ctrl-d` | remove (confirms) | `d` / `y` | inspect, as `o` (k9s's describe / yaml) |
| `H` | health: check, streak, last probes with output | `T` / `D` / `S` | top (processes) / diff (files changed) / full stats |
| `/` | filter: regex (leading `!` negates), `-f` fuzzy, `-l` labels | `:` | command palette |
| `ctrl-g` | toggle breadcrumbs (k9s) | `ctrl-e` | toggle the header (k9s) |
| `q` | back out of a drill-in (never quits) | `ctrl-r` | reload, as `r` |
| `[` / `]` | view history back / forward | `-` | toggle to the last view |
| `ctrl-a` | every command and alias (k9s's aliases view) | | |

Navigation is tuikit's `viewfsm.TranslateNavKey` — `j`/`k`/`h`/`l`, `g`/`G`, `ctrl-f`/`ctrl-b` onto the arrow and page keys — applied **after** the view's own keys, so a view's letter (`l` for logs) wins. In a log view the digits pick a time range (`0` the usual backlog, `1`–`5` the last 1m–1h) rather than switching views — a view claims them by implementing `views.DigitClaimer`. The log keys are k9s's (#3): `s` toggles autoscroll, `t` timestamps, `w` wraps, `f` hides header and crumbs until the log is left, `c` / `ctrl-s` copy / save what is shown (filtered, styling stripped; saves go to `$XDG_STATE_HOME/dockmaster/logs`), `shift-c` clears, `m` marks (a stamped rule appended to the buffer, k9s's mark — a tuikit `tail` marker, so every filter lets it through). Help over a log swaps the CONTAINER column for LOGS. `d` and `y`, k9s's describe and yaml, fall back to `o` in any view that does not bind them (`App.activeViewHandleKey`). Where k9s and Docker mean different things the key stays dockmaster's: `p` pause, `a` show stopped, `ctrl-k` Kubernetes containers (k9s's kill — `K` kills here, after a confirm). The events stream still toggles follow with `f`: that binding is tuikit's `tail.HandleScrollKey`, shared with every app on the chrome. `aliases.yaml` (`config.LoadAliases`, checked by `tui.ValidateAliases` before the UI starts) maps `:` names to command lines; `dispatchCommand` expands them first. `ctrl-a` and `:aliases` open k9s's aliases view (`views.AliasesView`, `tui/commands.go`): `commandRows` lists the user's aliases first, marked `alias`, then every view under its `ViewCommandNames` name with its other `viewCommands` spellings, then `otherCommands` — the hand-kept table of the rest with their spellings and a description, which `TestAliasesViewCoversEveryCommand` holds to `knownCommands` and `viewCommands`. `enter` returns `run_command` (`App.runCommand`, `dispatchCommand` as if typed) or, for a command that needs an argument (`:pull`), `palette`, which opens the bar on it. `ctrl+a` is answered in `handleKey`'s switch, after the bars — inside `:` and `/` it stays textinput's line-start — and is in `reservedKeys`, so no hotkey or plugin takes it. `expand` accepts every spelling in `otherCommands` (`isOtherSpelling`: `x`, `log`, `h`…), so a hotkey or `-c` may use one, without reserving it from aliases. A view command takes a `/filter` argument and an `@context` word (#18, k9s's): `cutContextArg` takes it from before the filter, so an `@` in a filter stays the user's text, and `viewInContext` switches context with a `landing` — `applySwitchContext` opens that view and filter instead of containers — or, naming the context on screen, just opens the view. Any other command that opens a view takes `@context` too (#57): its `landing` carries the command, run after the switch; quitting and `:ctx` refuse it. `-c` / `defaultView` take any command or alias, checked by `ValidateCommand` (aliases expanded first); one that is not a table view is run from `App.Init` as if typed. `hotkeys.yaml` (`config.LoadHotKeys`, validated by `tui.HotKeys`) binds keys to `:` commands; `handleKey` asks them after the view and table keys, before navigation, so a view's own key wins — unless the hotkey sets `override` (#58, k9s's), which asks it right after `override` plugins, before the view. `keepHistory` (k9s's) sets `App.keepStack` while the hotkey's command runs, and `switchView` then pushes (`pushTopView`) instead of clearing the stack, so `esc` comes back — unless the view is already on the stack, which is switched to as before. `plugins.yaml` (`config.LoadPlugins`, validated by `tui.Plugins`) runs the user's commands on the selected row (`tui/plugins.go`): `$VAR`s in args are expanded by dockmaster from `pluginVars`, an `override` plugin is asked before the view's keys, the rest after. `overwriteOutput` (k9s's) puts a successful background plugin's first non-blank stdout line, ANSI and controls stripped (`firstLine`), in the flash instead of "done"; stdout and stderr go to two writers then, so the combined buffer is a `lockedBuffer`. k9s's `inputs` open a form first (`views.PluginFormView`; `App.pluginPending` keeps the row's vars while it is up) whose values become `INPUT_<NAME>` in args and env, confirm defaulting on; `pipes` run as a pipeline built in Go (`tui/pipeline.go`, a `tea.ExecCommand`, seam `execPipelineFn`) — every command exec'd, no shell — with `$VAR`s not expanded in them, as in k9s. A pipe of fewer than two words, an input k9s would accept but run differently, and `background` with pipes are refused at startup (`docs/design/config.md`). Skins are k9s's (`ui.skin`, `DOCKMASTER_SKIN`, `--invert`; `docs/design/config.md`): ⚠️ every package-level style must be derived in `style.apply` or a view's `applyTheme` (registered with `style.OnBase`), never in its declaration — a declaration runs before the skin loads. `TestNoPackageStyleSkipsTheSkin` enforces it, and tables repaint with `tktable.FixRows`, never `FixSelectedRow`, whose colors are fixed. `enter` on a volume browses it (`o` inspects): the browser walks directories in place and claims `esc`/`q` through `views.Backer` until it is back at the volume's root. Inspect and the reports that share its view (health, diff, stats, a machine's or a pod's description) take k9s's describe keys (#6): `/` searches rather than filters — `InspectView.SetFilter` calls tuikit's `tail.SetSearch`, which highlights matches and hides nothing, then jumps to the first; `n` / `N` step through them and `Status()` puts "3/17" in the title — `c` / `ctrl-s` copy / save the whole document — saves go to `dumps/`, so `:sd` lists them — `f` fullscreen, and `a` toggles refreshing on the poll for that view, overriding `liveViewAutoRefresh` (`App.inspectAutoRefresh`). `v` scans an image for vulnerabilities (#11): `internal/scan` (no bubbletea) finds `grype` or `trivy` on PATH, runs it with `DOCKER_HOST` set to dockmaster's daemon, and reads either report into one `Vuln` shape, worst first — its parser is tested against real reports trimmed into `internal/scan/testdata`. A container scans the image it was created from, by ID. `views.ScanView` (seam `views.RunScan`) is `Stoppable`: leaving it cancels the scanner, and a result from a scan since restarted is dropped by generation. `:lint` is container lint (#10): `docker.LintContainer` is a pure function from one container's inspect data to findings (risk / warn / info, worst first), so every rule is tested on hand-built inspect data; `Client.Lint` inspects every container, stopped ones included, at most 8 at once, and reports an inspect failure on its row. A kind/k3d node's privilege is info, not risk — it needs it. The view (`views.LintView`, seam `views.RunLint`) loads on open and on `r`, never on the poll: it is one inspect per container. `U` on an image, volume or network opens the containers using it (#8): `App.showUsedBy` gives the containers view a scope (`ContainersView.SetScope`, shown in the title as "using image nginx") and pushes it, so `esc` returns; the scope lifts when the view is left (`clearContainerScope`). Matching is exact — an image by the container's `ImageID`, never the tag, which can move; a volume by the named mounts in `Container.Volumes`; a network by `Endpoints`. `J` on a container jumps to its compose project. The `:` and `/` bars recall earlier entries with up/down (tuikit's bar history, #13); suggestions cycle on ctrl+n/ctrl+p. `tui/history.go` keeps that history across runs in `<state>/history.json` — `Options.HistoryFile`, set by `main.go`, so tests never touch the real state directory — leaving out quit commands, which the bar records before running them. The filter is tuikit's `RowFilter` (#7): a regex by default, `-f term` fuzzy, `-l selector` over labels. Containers, images, volumes and networks filter with `f.Match(fields, labels)`, so `-l com.docker.compose.service=web` works; every other view uses `MatchesAny`, which a label filter never satisfies, so `onFilterChange` says why the list emptied (`labelledViews`). `c` and `i` copy the selected row's name and full ID in any table whose view implements `views.Copier` (`views/copy.go`; `App.copyRow` hands the text to the terminal with `tea.SetClipboard`, OSC 52, so it works over ssh); they are table keys, so a view that binds `c` itself — the log's copy — keeps it. Every table view shares three tuikit features through `internal/tui/table.go` and `views/{table_rows,sort,marks}.go`: `ctrl+s` saves the table (`table.PlainText` into `chrome.SaveDump`, under `$XDG_STATE_HOME/dockmaster/dumps`, and `:sd` — `views.DumpsView` — lists both that and `logs/`, reads a save back in the plain viewer, and deletes one after a confirm, refusing any path outside those two directories); `shift+←/→` / `shift+↑/↓` sort by column and direction (`table.Sorter`, off until first pressed so each view keeps its own order, with ages and sizes compared by what they measure); and in the containers, images, volumes and networks views `space` / `ctrl+space` / `ctrl+\` mark rows (`table.Marks`), after which lifecycle and remove keys act on every marked row, one confirm for the destructive ones. ⚠️ A view's `Selected` indexes its `visible` slice by cursor, so `sortRows` reorders `visible` with the rows — sorting the rows alone would act on the wrong container. Marks key on IDs, not the name cell, which is truncated and could match two containers. In the logs and events streams, keys and the mouse wheel go through tuikit's `tail.HandleScrollKey` (`views/scroll.go`): any scroll pauses follow so new lines stop pulling the view down, and `G` resumes it, as in k9s. The help overlay's GENERAL and NAVIGATION columns are tuikit's shared `chrome.GeneralHelp()` / `NavigationHelp()`; `TestNavigationKeysDoWhatHelpSays` drives every advertised navigation key.

`:xray` (#9) is tuikit's `tree` (v0.0.20) over one `docker ps -a`: projects → services → containers → image, volumes, networks (`views.XrayView`, `SetDefaultDepth(-1)` to open everything as k9s does). Each node ID maps to what `enter` and `o` do on it (`xrayTarget`); the tree's own keys (space, h/l) are claimed in `HandleKey` and the rest of the navigation arrives through `UpdateTable` already translated. On a container node the container keys (#56) — `s` `A` `u` `x` `R` `K` `p` `ctrl-d` `v` — return what the containers view returns, through the one `views.containerAction` both views call, so `--readonly`, the confirms and the refresh after are `handleAction`'s; `v` on an image node scans it; `c` / `i` copy because `XrayView` is a `views.Copier` (`tableKey` asks any Copier, table or not); `ctrl-d` off a container is claimed as a no-op rather than paging the cursor onto one; and `containerName` reads the tree's names, so the confirm and flash name the container. It is polled like containers, and `SetRoots` keeps what is open and the cursor across refreshes. `:pulses` / `:pu` (#12) is k9s's pulses (`views.PulsesView`, tuikit's `chart`, v0.0.21): three gauges across the top, CPU and memory sparklines side by side under them, the event rate across the bottom. Each panel's data and what it costs: **Containers** (running / total, no thresholds — a stopped container is a choice, not a fault) and **Health** (healthy / those with a healthcheck; critical when any is unhealthy, warn while one is starting) come from one `docker ps -a` per poll tick. **CPU** (docker stats' CPU % summed over the running containers, full height = 100 × the daemon's CPUs) and **Memory** (summed usage, full height = the largest limit seen, which for an unlimited container is the daemon host's memory) come from `Client.SampleStats` — the containers view's sampler, one blocking request per running container — chained after that listing, so list and sample are one flight; with the CPU/MEM poll off (`--no-stats`, or `t` in containers, synced on open) they say so and never sample. **Reclaimable** (summed reclaimable / summed size of `docker system df`'s four rows; warn at half) is the expensive one: read on open, on `r`, and then every minute of polls (`pulseDiskEvery`), never two at once. **Events** is one `StreamEvents` subscription from now on, held while the view is open and cancelled by `Stop` when it is left (the view is `Stoppable`); a drain blocks until an event arrives, so a quiet daemon costs no wakeups, and each tick pushes the count since the last. Ticks reach the view through `views.Poller` (`Poll`, not `Refresh`, so opening or `r` neither closes an interval nor reads disk out of turn). The series hold ten minutes at the poll rate (at least 120 samples) and start over when the view is reopened. Its messages carry the instance that asked, are routed to it whichever view is showing (so a guard is never left set), and a stale one — another context's, a restarted stream's — is dropped. Seam: `views.PulseSourceFor`; `PulsesView.Drains()` counts running drains, so tests prove nothing is left behind after leaving. `:dir [path]` (#15) browses the local filesystem for compose files (`views.DirView`, a `Backer` like the volume browser): `u` runs `compose -f <file> up -d` for a project that has no containers yet — `fileProject` leaves `Project.Name` empty, and `ComposeArgs` omits `-p` then, so compose names it from the file or its directory, as from a shell — and `e` edits the file then brings it up (`composeEditedMsg.file`), and `ctrl-d` confirms naming the file, then runs `compose -f <file> down` (`composeFileDown`, the same `fileProject`). All three are in `mutating`, and each answers anything but a compose file with `not_compose`. In the projects view `l` opens the project's merged log (`docker.StreamProjectLogs`: `MergeLogs` fans in every member's stream, tags each line with `LogLine.Source`, and follows `start` events so containers started later join from that moment; `views.NewProjectLogsView` prefixes and aligns them, and its container-only keys are inert). The other letters run Compose — `u` `compose up -d`, `e` edit the compose files in `$EDITOR` then `up -d` if they changed, `R` restart, `p` pull, `s` scale a service (#62), `ctrl-d` `compose down` (confirms) — via the `docker compose` CLI against the files the project's labels record, falling back to per-container actions when those files are not on this machine (`docs/design/compose.md`). `s` opens `views.ScaleFormView` (the service a choice over the project's, replicas prefilled from `Project.Replicas`, every container of the service, stopped ones too); its `compose_scale` action is `Compose.Scale`, `up -d --scale svc=N --no-recreate svc`, and a count below the current one confirms. Scale has no per-container fallback, so missing files refuse it. On `:xray` `s` on a project or service node opens the same form (`XrayView.Project` folds the listing, so `composeProject` finds the project without the projects view).

In the runtimes view the same letters act on the machine, where its runtime supports the verb (see `docs/design/runtimes.md`): `n` new machine (the form's Provider field picks the runtime) and `e` edit resources (both a form, `views.RuntimeFormView`, which captures every key but esc), `o` inspect, `u` start, `x` stop, `R` restart, `ctrl-d` delete — the last three confirm, since each takes every container in the VM with it — `s` ssh into the VM (Colima, Podman) or, on a Docker Desktop / OrbStack / Rancher Desktop row, the host shell below on that runtime's socket, `K` manages a kind cluster on the machine's daemon (after a confirm): stops or starts the one there, or creates one — control-plane + worker plus `kind-registry` on `localhost:5001`, the user's own setup — via `internal/kind` and `docker.Clusters`/`EnsureRegistry`/`WireRegistry`. The registry stays its own container (it outlives the cluster) but is treated as part of it: `K` stops and starts it with the nodes — stopping only with the last kind cluster using it — it is marked ⎈ in the containers list, and the node view shows where to push. It never switches a runtime's built-in Kubernetes, and refuses where one is on or the machine is stopped. `enter` connects dockmaster to the profile's daemon. See `docs/design/colima.md`.

`n` on a kind or k3d node container (marked ⎈) opens the node view (`c` is k9s's copy key): the containers inside the node's own containerd (every pod), which `docker ps` never shows. They are read with `crictl` over a docker exec; `enter`/`l` logs, `o` inspect, `s` shell, `ctrl-d` remove (exited only, confirmed), `a` show exited (hidden by default). See `docs/design/kubernetes-nodes.md` — in particular why node log streams run under a watcher.

`u` on an image opens the run form (`views.RunFormView`): name, ports, env, volumes, command, `--rm`, each list space-separated as after `-p`/`-e`/`-v`. It is checked with `docker.RunConfig` — the same code that builds the create request — so a bad port is reported in the form; a daemon failure lands back in the form, and success opens the new container's logs. A container that is created but will not start is removed. The runtime and run forms share their field machinery in `views/form.go`.

`C` on a container is `docker cp` either way (`views.CopyFormView`): the archive handling is moby/go-archive, the docker CLI's own, so directory-versus-contents and missing-destination rules match `docker cp` — checked against the real CLI on the same input. Copying in changes the container and is gated by `--readonly`; copying out is not. A local path takes `~` and is relative to where dockmaster was started.

`e` on a container edits it in place (`views.EditFormView`, `docker.Edit`): CPU and memory limits and restart policy via `docker update`, the name via `docker rename` — no restart. The form opens on the container's current settings. A memory change always carries a swap value: the daemon refuses memory above the existing memory+swap limit ("update the memoryswap at the same time"), so `docker.EditUpdate` keeps the swap headroom the container had (unlimited stays unlimited; no limit before gets docker run's 2×). Checked live.

`K` and every `ctrl-d` are uppercase or modified on purpose: the violent operations should not share a keystroke shape with navigation.

`s` honors config's `shell` (#18): `preferredShellProbe` runs it when the container has it and falls back to bash-then-sh, with the name passed as `$0`. `dockerExecIt` hands the terminal over through `inTerminal`, so tests capture the command. `A` attaches to a running container's main process (#16): `App.attach` runs `docker attach --sig-proxy=false` through a one-line `sh` that prints the way out first and passes every argument positionally. `--sig-proxy=false` matters — by default a ctrl-c in the attached terminal becomes SIGINT to the container, which stops most services. It is in `mutating`, as `exec` is, so `--readonly` refuses it. `s` shells out to the `docker` CLI via `tea.ExecProcess` rather than driving the SDK's hijacked-stream exec. Interactive sessions need raw-mode TTY handling, window-resize propagation, and signal forwarding; the CLI already does all three correctly. It passes `Client.EndpointArgs` (`--host`, or `--context` for a TLS context) so an exec always lands on the daemon dockmaster is showing, not whatever context the user's shell happens to have.

`:hostshell` (#59, k9s's node shell) is a **root shell on the daemon's host**: `docker <EndpointArgs> run --rm -it --privileged --pid=host --net=host --label dockmaster.helper=hostshell <image> nsenter -t 1 -m -u -i -n -p -- sh` (`docker.HostShellArgs`), through `inTerminal` like `s`. The image is config's `hostShell.image` (default `alpine:3`, whose busybox has `nsenter`); one starting with `-` is refused, at load and before the confirm, since docker would read it as a flag. `confirm_host_shell` is in `mutating`; it always confirms, naming the daemon and image and saying it is root there; the image and endpoint are fixed in the confirm's param, and the confirmed run re-checks readonly (a reload can flip it). A rootless daemon (`Client.Rootless`, `name=rootless` in `/info`'s security options — docker and podman alike) is refused with a reason. See `docs/design/host-shell.md`.

## The log and `dockmaster info`

`internal/applog` opens `<state>/dockmaster.log` (`--log-file` replaces the path, `--log-level` debug/info/warn/error, default warn; flags only — the log is open before config.yaml is read) append-only, 0600, in a 0700 directory, and rotates it once to `.1` when a write would take it past 5 MB. `main.go` opens it and hands `tui.Options.Logger` to the app; nil logs nothing, which is every test that does not ask. **Every error flash is logged at one choke point**: `App.Update` wraps the dispatch (`update`) and calls `logFlash`, which writes `errFlash` when it differs from `loggedFlash` — so none of the ~80 places that set `errFlash` needs to know about the log, and a flash still showing on the poll is written once. `handleKey` clears both when a key clears the flash, so the same error shown again is logged again. Plugin runs (name, command, input *names*), their end (a background run's exit status, a failure's reason), hotkey runs and context switches are info lines (`tui/logging.go`). ⚠️ **Never log a plugin's arguments, environment or output, or an input's value**: args are expanded from the inputs and the row, and the output can echo them. A failed plugin's flash carries its last output line, so `handlePluginDone` logs the status alone and marks that flash logged; `TestPluginInputValueIsNotLogged` types a secret into a form and fails if it reaches the file.

`dockmaster info` (`internal/info`) prints the config dir and file, skins dir, state dir, dumps and saved logs (under `screenDumpDir` when set), log file, history, version, and the context and endpoint dockmaster would use with how it chose them — `info.Endpoint` mirrors main's precedence (`--host`, `$DOCKER_HOST`, `--context`, `$DOCKER_CONTEXT`, config.yaml's `context`, the CLI's current context, the default socket) and reads only the context store. It never dials, prints no environment value beyond the endpoint, and masks a password in an endpoint URL. It takes `--host`, `--context` and `--log-file` so it can answer for a given command line.

## Configuration

`config.yaml` is shaped after k9s's (`dockmaster:` root, `ui:` and `logger:` blocks) and read from `$DOCKMASTER_CONFIG_DIR`, else `$XDG_CONFIG_HOME/dockmaster`, else `~/.config/dockmaster`. **Only flags set on the command line override it** — `flag.Visit`, never the parsed default — and unknown keys are an error, not ignored. Adding a setting means a key in `config.Config`, its default in `Default()` *and* `Sample` (`TestSampleIsTheDefaults` fails otherwise), and, if it has a flag, a row in `applyFlags`. See `docs/design/config.md`.

`contexts:` (#55) gives a docker context, by name, its own `skin`, `readOnly` and `defaultView` (`config.ContextSettings`; `main.go` loads each skin with `config.ContextThemes` and checks each `defaultView` with `tui.ValidateContextCommand`, at startup and on reload, into `tui.Options.Contexts`). They apply at startup and in `applySwitchContext` (`App.applyContextSettings`), which reskins through `App.reskin` — `style.SetBase` then `buildChrome`, the reload's path — and recomputes readOnly: `--readonly` (`Options.ForceReadOnly`) beats the context's `readOnly`, which beats the top-level one; `:readonly` lasts until the next switch. `DOCKMASTER_SKIN` beats a context's skin. The top-level view last open on each context is remembered in `<state>/contexts.json` (`Options.ContextStateFile`, set by `main.go`; `rememberView` in `showView`) and restored by a switch with no landing of its own, and at startup when neither `-c`, the context's nor the top-level `defaultView` says otherwise. Nothing writes `config.yaml`.

`views.yaml` (#14; `config.LoadViews`, validated by `tui.ColumnLayouts` against `views.ColumnTitles`) chooses each table view's columns, their order and its default sort. It is applied at **two choke points in `views/sort.go` and `views/layout.go`, and nowhere else**: a view's columns go through `tableSort.layout(fullColumns, width)` (project, then `fitColumns`, then widen the last column to the screen, then the sort indicator) and its rows through `sortRows` (project, then sort, reordering `visible` with them). Each view names itself in its constructor (`tableSort{layoutKey: "containers"}`) and the layouts are package state, `views.SetColumnLayouts`, set by `NewApp` and by a reload (`App.applyColumnLayouts`, which calls every open view's `Relayout`). ⚠️ The projection is **by title, recomputed from the current titles every time — never cached by index**: the containers view's wide mode adds columns in the middle, so an index mapping from one mode puts the wrong cells under the other's headers. A title not in the current set is skipped; the untitled marker column (contexts, runtimes) always leads. Because rows are projected before sorting, the sorter's column counts the columns the user sees, and `remapSort` / `followSort` compare displayed titles. A view not in the file goes through the same functions with a nil projection and behaves exactly as before. A new table view needs its key in the constructor, its column function in `columnSets`, a `Relayout` method and a row in `docs/design/config.md`'s views table. **Expression columns** (#61, k9s's `TITLE:<path>|attrs`; `views/expr.go`) read `.Labels.<key>` (dots escaped `\.`) or a field from the row's own data — never another daemon call — in the containers, images, volumes and networks views (`exprSources`, an explicit field table per view, named after the Engine API's list fields; `ParseExprColumn` checks the path and attributes against it, and `tui.ColumnLayouts` refuses a title that is one of the view's own or listed twice). They go through the same two choke points: `titlesOf` appends the shown expression titles after the column set's (a `W` one only with the wide set, read from the titles, not remembered), and `sortRows` reads each row's expression cells from `items[i]` — the item it was built from — *before* the sort, then projects, so the cells move with their row and `visible` with both. That is the seam: a view needs no code of its own beyond handing `sortRows` the items its rows were built from, and a view joins `exprSources` only if it does. `R` pads cells to the width `layout` recorded by title (`fillWidth` passes over an R column); `N` is `tableSort.compare`, looked up by the shown title; `T` draws an age, which `cellCompare` already sorts. Every other attribute is refused at load, never ignored. Cells are cleaned of control characters — a label is anybody's text.

## Testing

- `internal/tui/app_test.go` drives the real root model headlessly: feed messages, render, assert. **Assertions strip ANSI first** — lipgloss emits a separate escape pair around *every character* of an underlined span, so a substring check for the help overlay's `RESOURCE` header can never match the raw frame. `render()` strips; `renderStyled()` is for the few assertions that are genuinely about color.
- The views are driven through the app rather than unit-tested in isolation, so the tests cover the wiring (key → action → state → frame) that is where the bugs actually are.
- The colima tests use a fake `Runner` and never touch a VM. `internal/colima/live_test.go` lists the real profiles read-only and is skipped under `-short`. **Never write a test that starts, stops or deletes a real profile** — it is the daemon every other test and the user's own work runs on.
- Fuzz targets guard what untrusted input reaches: `FuzzSanitizeLogText` (container output — no escape but complete color sequences, no C0 or C1 controls), `FuzzExpandPluginVars` (a value is substituted once, never re-expanded), `FuzzParseShortcut`, `FuzzParse` (config) and `FuzzParseExprColumn` (a views.yaml expression column parses back from its own path). Their seeds run as ordinary tests; fuzz one with `go test -run '^$' -fuzz '^FuzzSanitizeLogText$' -fuzztime 30s ./internal/tui/views`, and commit any input it finds under `testdata/fuzz/`.
- `TestEmptyFilterDoesNotWedgeTheCursor` pins a bubbles quirk: `SetRows` clamps the cursor to `-1` on an empty row set and never restores it, silently killing every row action for the rest of the session. `setTableRows` exists solely to repair that, and any filter matching nothing reaches it — including an ordinary `docker ps` right after the last container stops.
